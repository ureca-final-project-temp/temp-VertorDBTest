# 현재 실험 프로토콜

목적은 **검색 파라미터 변화에 따른 Recall–Latency–Resource 전체 trade-off를 산포도로 보여주는 것**입니다. Recall@10 0.90과 0.95는 결과를 해석하는 reference quality level입니다. 허용 구간, PASS/FAIL, 결과 제거, 측정 조기 종료의 기준으로 사용하지 않습니다.

## 실행 단위와 고정 조건

| 항목 | 현재 설정 |
|---|---|
| 입력 | 합성 청크 10,000건, BGE-M3 dense 1024차원, COSINE |
| 검색 | Top-10, concurrency 10 |
| 질의 | SHA-256 층화 분할: 진단용 calibration 100 / evaluation 200(무필터 180 + 필터 20) |
| 파라미터 | matrix에 명시한 검색 폭을 전부 측정; Recall을 보고 후보를 선택하지 않음 |
| 워밍업과 측정 | 각 파라미터에서 evaluation 1회 워밍업, 5회 검색 단위를 최소 5초 이상 반복(최소 1,000요청) |
| 반복 | 실행 스크립트는 전체 재구축 3~5회, 동일한 파라미터 그리드 재사용 |
| 자원 | 대상 합계 4 vCPU / 8 GiB / swap 없음; Milvus는 본체·etcd·MinIO 합계 |

행렬은 14개 DB + Engine + Index 구성입니다. 과거 ID와 연결하기 위해 T01, T03, …, T27을 유지합니다. 과거의 짝수 ID는 별도 품질 목표 행이어서 새 행렬에는 없습니다. 현재 그리드는 재구축 회차당 124개 파라미터 점을 측정합니다. [2026-09-11 전체 sweep 실험](../07-results/sweep-results-20260911.md)에서 14개 구성을 각각 3회 재구축해 **372개 실측 점을 모두 저장·검증**했습니다. 총 42회 재구축, 본 측정 검색 2,948,000회이며 CPU·RAM 누락과 실행 오류는 0건입니다.

## 측정 순서

1. 전체 파라미터가 어댑터의 지원 범위 안인지 검증합니다.
2. 같은 문서 벡터로 인덱스를 재구축·적재하고 준비 상태를 확인합니다.
3. 동일한 벡터·필터의 Exact Top-K 정답을 계산합니다.
4. 각 검색 파라미터를 적용하고 evaluation 워밍업을 수행합니다.
5. Recall, 평균/p50/p95/p99 latency, QPS, CPU·RAM 평균/최대와 부가 비용을 측정합니다.
6. 해당 점을 원시 JSON에 즉시 보존하고 CSV·집계·산포도를 갱신합니다.
7. 다음 파라미터와 반복으로 진행합니다. Recall이 0.90 또는 0.95를 넘어도 계속합니다.

나중 검색에서 실행 오류가 발생하면 실패한 파라미터를 `failures/`에 기록하고 요청을 중단합니다. 앞서 완료한 측정은 보존합니다. 실행 오류와 낮은 Recall은 다른 문제입니다.

## 산포도와 비교

- X축: 전체 evaluation의 p95 latency(ms).
- Y축: 같은 evaluation의 actual Recall@10.
- 모든 반복의 실제 점을 표시합니다. 집계 평균이나 보정값으로 점을 대체하지 않습니다.
- 색은 DB + Engine + Index, 점의 tooltip은 검색·생성 파라미터, 반복 번호, Recall, latency, QPS, CPU, RAM을 표시합니다.
- Recall 0.90과 0.95를 수평 참고선으로 표시합니다.

주 비교 질문은 “Recall 약 0.90 이상에서 어느 구성이 latency와 자원을 적게 사용하는가”, “약 0.95 이상에서는 어떠한가”입니다. 필요하면 측정 파라미터를 증가시키며 해당 수준을 처음 넘는 실제 점을 대표로 고를 수 있습니다. 0.943과 0.961 중 0.95 참고 수준의 대표를 0.961로 골라도 0.943은 전체 분석에 남습니다.

필터·무필터 세부 지표도 함께 보존합니다. 무필터 Recall을 전체 p95와 짝지어 같은 모집단인 것처럼 해석하지 않습니다.

## 반복과 집계

API의 `repetitions`는 같은 인덱스에서 그리드 전체를 반복합니다(기본 3). 실행 스크립트는 API에 1을 전달하고 외부에서 재구축을 반복합니다. `measurementIterations=5`는 한 점 안의 질의 집합 반복이며 독립 측정 5개를 뜻하지 않습니다.

집계 키는 DB/engine/index, 생성·검색 파라미터, 벡터 수, Top-K, 부하와 입력 해시·실행 환경입니다. test ID나 참고 Recall로 묶지 않습니다. 동일 파라미터의 평균, median, p95/p99, min/max, 표본분산과 표본 수를 저장합니다. 집계 p95/p99는 반복 측정 지표 사이의 분위수이며 전체 요청을 합친 분위수가 아닙니다.

각 점은 최소 5초간 완전한 질의 단위를 반복해 측정합니다. 실제 요청 수와 measurementTimeMs를 기록하며 query 유형의 비율을 유지합니다. CPU/RAM은 수집 시작·종료가 모두 검색 구간 안인 Docker 표본만 사용하고 resourceSamples를 기록합니다. 원시값 -1은 수집 불가이며 집계에서는 null과 유효 표본 수로 표시합니다. 3회 반복의 p95/p99는 사실상 최댓값이므로 넓은 신뢰구간을 보장하지 않습니다.

## 정답과 진단

Exact 정답이 비어 있으면 Recall 평균에서 제외하고 빈 결과 반환 여부를 별도로 집계합니다. 이는 낮은 Recall 측정값을 버리는 규칙이 아닙니다. `*_scored_queries`, `*_empty_ground_truth_queries`, `*_empty_ground_truth_violations`를 보존합니다.

Milvus는 진단용 무필터 질의를 직렬·동시성으로 각각 3회 추가 실행합니다. 첫 동시성 표본 대비 편차와 직렬/동시성 median 차이, 전후 상태를 기록합니다. 이 진단은 타이머 밖에서 실행하며 산포도 포함 여부나 구성 탈락 조건으로 사용하지 않습니다.
